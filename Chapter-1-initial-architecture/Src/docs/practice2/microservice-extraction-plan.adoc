= Microservice Extraction Plan: Passes Module

== API of the Microservice
The microservice will provide a REST (or gRPC) API for synchronous interaction:
* `POST /api/passes` - Register a new pass.
* `PATCH /api/passes/{id}/expire` - Mark a pass as invalid.
* `GET /api/passes` - Get a list of client passes.

== Data Ownership
* The microservice will have its own physical database (e.g. PostgreSQL).
* The `Passes` table will be owned by this service.
* Other services will not access this database directly.

== Communication with Other Modules
* Consume events: subscribe to `ContractSignedEvent` to create passes.
* Publish events: publish `PassExpiredEvent` when a pass expires.
* Use a message broker (e.g. RabbitMQ or Kafka) and the Outbox pattern for reliable delivery.

== Public Facade
Expose a single application service interface `IPassService` (synchronous or gRPC) that other modules use to interact with Passes.

== Notes
Keep the module small, owning its domain and persistence. Use asynchronous events for integration.
